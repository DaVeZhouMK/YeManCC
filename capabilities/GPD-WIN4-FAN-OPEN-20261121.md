[Win4's HC Open](../deps/handheldcompanion-runtime/source/Devices/GPD/GPDWin4.cs#L114) requires its EC identity read to match before the original unlock. [OpenLibSys](../deps/handheldcompanion-runtime/source/Misc/OpenLibSys.cs#L50) selects slot 0 only for the index port `0x2e`; the paired data port `0x2f` gets slot 1 in both read and write methods. The same selector is present in the actual HC `4cd3dea2…` method IL, not just in the source baseline. The exact LpcIO module extracted from the matching release `LibreHardwareMonitorLib.dll` (`f7ed30f0…`) matches PawnIO.Modules release `0.1.6` byte for byte (`3dcf8b2b…`); its [slot and port check](https://github.com/namazso/PawnIO.Modules/blob/4aa792beb020a14c8261072e9786d2dfb38489d9/LpcIO.p#L117) puts both ports in slot 0 and rejects the data port under slot 1 after selection. The existing logs omit the actual device read result and IOCTL return. The confirmed mismatch can explain the field refusal, but the logs cannot establish that this was the only fault on the unit.

[Candidate tool](../tools/hc-device-runtime/New-GpdWin4FanPortCandidate.ps1) reproduces the mismatch using the actual integer selector IL from both pinned methods and a fixture for the pinned module's port pairing. Both original paths reject the data port; both corrected paths accept it. All 131,070 other method/port assignments remain identical and exactly ten bytes changed in two expressions. The candidate is `f79edd9dc1c60d5b5e9f3c456174b3c049ea6087ea0c988facd95bc1c174b93c`; it keeps the same HC API, chip verification, unlock, duty and return methods. No HC assembly or hardware path is executed by the fixture.

The production profile, runtime manifest, export lock and LightSetter pin select the new hash. Release preflight checks the corrected HC identity in addition to the existing Host pins. The ordinary export also checks the runtime at source, stage and final ZIP.
