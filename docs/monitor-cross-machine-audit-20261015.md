## 新确认并修正：多电池数据被误当整机数据

原解析逻辑每读到一个 HWiNFO 电池 Rate 或 Remaining Time 就覆盖输出。因此双电池组分别为 -8W/-4W 时，最后一组 -4W 会被误当整机功率；两个电池组的时长也只剩最后一组。若剩余能量却来自 Windows 汇总，这种混用还会导致时长偏大。

修正：

1. 在既有解析循环中记录电池功率和时长的 sensorIndex。发现多个电池来源组时，拒绝把最后一组当整机数据。未盲目相加可能重复的别名或汇总组。
2. 既有 Windows 电池查询缓存已确认多个系统电池时，不采用可能只覆盖一个电池的 HWiNFO 功率/时长，继续使用原有 Windows 完整汇总与降级链路。
3. Windows 电池数量取自原有发现缓存，未增加枚举、读取、线程或轮询。
4. 单电池的瓦/毫瓦、正幅值 Discharge Rate、秒/分钟换算保持不变。

真实生产解析函数的反例先复现失败。修复后 27 个解析/发布场景通过；将修复前实际解析代码仅注入测试构建，两个多电池反例重新失败。详见 `parser/` 与 `parser-negative-control/`。这证明的是多电池机器类别上的代码缺陷，**不是声称 G3E 有多块电池或 G3E 日志已经发生了这两种错误**。

## 新修正：标准日志导出缺少监控状态

五份 G3E ZIP 都没有逐秒 top/fps 统一快照，也没有 `rtss.monitorOutput` 配置。因此不能从现有 ZIP 判断当时具体启用了哪些字段、哪张显卡、功率是否估算、某个空值属于哪条链路。

在现有 `logs.exportAll` 内增加 `monitor-export-state.json`：

- 仅复制 `monitorSnapshotServeFn()` 的已有缓存，保留 session/generation/seq/collectedAt、独立通道标记以及原始 top/fps 文本。
- 附带启动时已经缓存的机器身份及保存的 monitorOutput 配置。配置不存在时明确写不存在，不拿默认值冒充用户设置。
- 明确标记不增加采集需求、不读取硬件、不包含历史序列、缓存与配置不是原子联合快照。监控关闭/缓存无数据时保持无数据，不为了导出启动采集。
- 保存失败时只报告当前导出失败，不把之前遗留的导出快照打包成这一次的状态。
- 原生缓存中的 `top.tdpW` 仍是 CPU Package Power；前端 TDP runtime store 的当前确认态不在原生缓存里。生效上限还需与 tdp.log 中的对应回执核对，不能拿 top.tdpW 或保存配置代替。
