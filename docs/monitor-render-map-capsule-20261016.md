# 监控元数据查表复用与胶囊 720p 布局修复（2026-10-16）

本轮继续优化监控数据消费与 CPU 工作，持续目标仍进行中。生产修改只在 `src/components/MonitorHudTemplate.vue`；没有新增数据源、采集、轮询、计时器或线程，没有部署、重启 YMCC/Steam/游戏或实机游戏验证。

## 修复的布局问题

上轮保留的失败组合是：轻量胶囊、1280×720、200%、多个百分比字段及曲线/核心图块。胶囊只有字段全开达到 full 阈值时进入已有三列堆栈；部分字段横跨五个分区时仍按两列堆叠，导致高度越界。

现在把 capsule 加入已有的 dense 布局候选。判定依然使用“超过四个可见分区、非横板”，字段少的胶囊保留原来的紧凑布局。继续使用现有三列规则，不删除字段、不修改用户缩放、不减少曲线或核心图块。13px 基础字号保持，MEM 分区会沿用 dense 原有的 .88em 规格；这是已有分区字号策略，不是新增整体缩放算法。

同一组字段的修改前/后测量：

| 画布 | 缩放 | 修改前 | 修改后 |
| --- | --- | --- | --- |
| 1280×720 | 100% | 385.40625×364.53125 | 503.0625×239.328125 |
| 1280×720 | 140% | 539.546875×510.34375 | 704.21875×335.09375 |
| 1280×720 | 200% | 770.828125×729.296875 | 1006.125×478.890625 |

1920×1080 下同一内容的尺寸相同，说明它没有按窗口额外压缩。dense 对应的 FPS 强调字号仍由已有的显示策略决定；本轮没有新增自动缩放算法。

## 重复查表的优化

旧组件每次渲染会反复调用 `HUD_PERCENT_GRAPHS.find()` 找到数字对应的图形。每个图形在 v-if、class、data 属性等位置多次使用，同一轮又扫描相同数组。分区投影还会重新查找图形/来源元数据。

现在在组件创建时预先整理固定分区、标量与图形关系，并根据现有 visibleFields 创建一个 computed 的 inlineGraphs 表。数据值更新且可见性不变时，表和分区不重建，后续 lookup 直接按字段取值。字段开关和自动隐藏改变可见性时，仍会重新投影。

图形专属的 cpuPeak 来源保留图形专属身份，不会重新暴露已经移除的数字项目。百分比验证、缺失值、图形/数字独立开关、新鲜度、帧率家族显示逻辑保持原实现。

## 确定性工作证据

`monitor_render_metadata_selftest.mjs` 读取修改前冻结的 SFC 与当前 SFC，编译真实 Vue 组件；只为元数据 find 调用插入计数，显示和数据逻辑继续用实际组件。

- 连续 80 次数据更新：旧版 3680 次 find、20640 次条件比较；新版这两项均为 0。
- 8 次字段组合切换：旧版 160 次 find、2331 次条件比较；新版这两项均为 0。
- 新版在组件创建时有一次固定元数据整理；上述 0 指更新阶段，不代表组件没有初始化工作，也不代表没有其他计算/分配。
- 13 布局的精简、全开、部分百分比组合，及零值、未知、自动隐藏和独立开关，数据语义对照通过。
- 有意修复的胶囊组合检查修改后的宽高；其他组合比较原尺寸。
- 电路面板 140% 截图修改前/后 SHA256 完全一致。

这些只证明重复查表减少，不能换算成整机 CPU 占用或游戏 FPS 提升；没有运行 CPU 百分比压测。
