# 监控订阅身份与重入派发修复（2026-10-16）

本轮修复显示订阅在取消/重绑时的两个数据问题。生产修改仅 `src/bridge/monitorDisplayFeed.ts`；没有修改采集、原生时钟、TDP 写入流程、窗口或界面。

## 修改前实际复现

使用真实 display feed 模块、虚拟时间及同步回调：

1. 一批 value=1 的派发已开始。回调 A 发布 value=2，并取消后重新登记同一个回调 B。新 B 立即收到最新 2，旧派发列表随后又调用 B 并传入旧 1。事件为 `[0,2,1]`。
2. 同一个函数被两位 owner 订阅。原 Set 只保存一个函数身份；第一位 owner 取消时删除了唯一条目，第二位仍有效却收不到后续更新，待发定时器也会被误取消。
3. 真实 TDP runtime store/feed 处理合成写入回执时，换绑可形成 `[null,null,45,30]`。最后一个 30 来自旧批次；不是硬件真的从 45W 回落到 30W。首个简化负例也保存了 `[null,45,30]`。

上述 30W/45W 是用于区分更新顺序的测试数据，本轮未读取或改变本机实际功率。

## 修正

每次 subscribe 创建一个独立登记身份，保存原回调。派发列表保存登记身份，取消也只删除自己的登记。

- 新登记不能冒充已删除的旧批次条目，因此新 B 收到 2 后不再收到旧批次的 1。
- 两位 owner 使用相同函数仍有独立的释放权；取消一位后另一位继续接收，最后释放才停止待发通知。
- 直接调用原回调，没有增加通知包装函数、轮询、线程或新的定时器类型。
- 保留现有一致批次、重入 push 的合并、初始缓存通知、异常隔离、1Hz/200ms 节流、失效立即清除和取消定时器 token 保护。

新订阅的初始最新值与后续全局合并发布仍遵守既有合同。本轮针对旧批次身份误认，没有声称消除所有场景的同值后续通知。

## 数据与工作证据

新增 `monitor_feed_subscription_identity_selftest.mjs`：19 组通过。

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 重绑期间先收到新 2 | `[0,2,1]` | `[0,2]` |
| 重绑期间只有当前 1 | `[0,1,1]` | `[0,1]` |
| 两位 owner，同一函数，释放一位后发布 2 | 丢失 2 | 剩余 owner 收到 2 |
| runtime store 回执换绑 | `[null,null,45,30]` | `[null,null,45]` |

还覆盖待发期间释放一位、换为不同函数、同函数两位新 owner、普通重入发布、最后 owner 重绑、旧 disposer/旧定时器、异常与 dispose、TDP 共享绑定、五秒 pending 过期及 AC/DC 清除。

普通两个不同回调、200 次发布：修改前后均 402 次通知（含初始通知）、200 份派发数组、400 个复制条目、两次登记，均不创建定时器。200 次快速输入的前后事件及计数相同，最多一个待发定时器。

修复每次登记新增一个小身份对象；对象分配发生在订阅时，没有增加每次发布的数组数量。独立 owner 各自收到更新是正确行为，其通知数不与修改前漏发的数量做 CPU 收益比较。上述工作计数不是 CPU 百分比或堆内存测量。
