# 监控显示缓存的所有权与旧数据去重修复（2026-10-16）

本轮检查实际生产单例及两条显示分发通道，修复按可变对象引用缓存判断造成的漏更新，并隔离展示与控制读取结果。生产改动仅 monitorData.ts、monitorDisplayFeed.ts、monitorHudFreshness.ts。继续使用现有统一快照、原有采集与定时器，没有新增来源、硬件读取、轮询或显示线程。

## 修改前确定性复现

1. monitorSnapshotDisplayKey 缓存上一对象引用。同一可变对象的 CPU 使用率更新后仍返回旧键；外部冻结 getter 也能改变字段而保持相同引用。
2. monitorSnapshotHasFreshData 同时缓存对象引用与 now。同一时钟刻度内，独立 Windows CPU 数据由无效恢复有效仍返回旧的 false。对象冻结不保证 getter 的结果不变。
3. 旧文件/seq=0 兼容路径在时间戳不变时，28 个 CPU/FPS 数值及证明字段不会改变去重键。包括 CPU 功耗、温度、频率、FPS、1% LOW、PID/进程创建时间、来源、观察时间、截止时间和帧时间证明。
4. 普通读取的控制结果与被动显示曾共享同一返回对象。控制侧修改自己的功耗或曲线数组，会影响已经收到该对象的显示订阅者；首个显示订阅者修改数据也会影响另一通道。
5. 第一条通道的订阅回调同步发布 seq=2 后，旧 seq=1 仍能随后进入第二条通道。修改前第二通道顺序为 [2,1]，修改后只收到 [2]。

这些是冻结的修改前实际源码及生产单例在合成输入下的负例，不代表已确认用户此前实机跳动的唯一原因。

## 修复

公开的键和新鲜度函数对可变输入每次重新判断，不向外提供可伪造的缓存所有权标记。生产单例在现有生命周期、字段解析及停止边界处理之后，对自己创建的展示对象、top/FPS 容器和已归一化数组冻结，再由私有 WeakSet 授予共享计算资格。

两条生产显示通道继续共用一次键计算，以及同一时钟刻度的一次新鲜度计算。时钟变化必须重新判断；第一通道回调将时钟推进到真实截止时间之外的负例也已验证。公开函数无法凭外部 Object.freeze 得到这份所有权。

含对象型异常旧 FPS 元数据的包保留原字段形状，只冻结展示容器和已知数组，不冻结该未知对象，也不授予缓存资格；两通道各自重算。该分支有独立检查，避免兼容输入成为缓存信任捷径。

补齐去重键中的 CPU/FPS 数值与证明字段。旧文件/seq=0 路径额外比较最多 16 个可见核心/标签，以及最后 120 个历史点；标签仍按既有 24 字符边界取值。现代源沿用推进序号作为数组更新身份，不在每个高频包中再串行化核心/历史数组。

普通 readMonitorSnapshot 继续返回可修改、隔离的控制副本。为避免冻结或共享这份控制结果，本轮在该读取分支为被动显示再创建一份有界副本。高频 native push 直接冻结自己新解析的展示对象，不增加整快照 clone。检查了现有调用点：顶部轮询和 autofloat 常规 tick 是 1 秒，预览使用现有 readOnce；本轮没有改变调用频率。

两通道分发还持有本次 publicationVersion。如果第一通道回调已经发布了更新快照，旧分发不再把旧对象送入另一通道。不可用通知清理私有缓存引用；过期、会话/代际/序号、停止意图及超限拒收仍由原统一入口处理。

## 工作次数、成本与验证范围

一次正常高频生产推送，修改前后均为：一次键构建、一次同刻度新鲜度计算、0 次整快照 clone、0 个 native 命令。

200 次实际生产单例推送的虚拟时间重放，修改前后均为 200 次键构建、200 次新鲜度计算、0 次整快照 clone；普通通道 21 次通知、曲线通道 101 次通知，通知序列完整一致，最终无残余 timer。

一次冷启动的普通读取，快照读取次数仍为 1；完整 clone 从原有 1 次增加到 2 次，新增的一份用于显示/控制隔离。这里如实记录复制成本，不把可靠性修复说成无成本。键补充字段和冻结也有工作量；“函数计算次数相同”不能证明总指令数相同或整机 CPU 下降。没有执行 CPU 百分比压测。

新增 monitor_display_cache_selftest.mjs 共 13 组通过，覆盖上述负例、28 个缺失字段、数组工作上限、实际生产共享缓存/读写隔离、两个通道的回调更新顺序、异常元数据不获资格、时钟跨截止时间、200 次推送和迟到 read 不发布/不增加展示 clone。新测试开发时补齐了读取需求登记，并等待原有通道预算到期后再观察结果，没有为测试改变生产停止或显示预算。
