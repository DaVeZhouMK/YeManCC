# RTSS 帧数据探测与旧映射释放（2026-10-16）

持续目标：监控数据与 CPU 工作量优化，保持 YMCC 唯一数据层。本轮从实际现有源头适配器继续检查；上一回合已有正式上游入口和预览工作消除，属于 progress。本轮产品改动仅 native/monitor_rtss_frame.h，不改变其他任务的 main.cpp、数据协议、HWiNFO 配置和用户输出设置。

## 冻结版本复现

实际 Windows 命名映射测试复现两个现象：

1. 快速 RTSS 通道找不到游戏 PID 槽位时，每次 sample 都重新扫描全部 appCount。1024 槽位、20 次 100ms 调用中，旧版执行 20 次全表搜索、20480 次槽位 PID 读取。
2. 读取器持有映射及视图，测试生产者关闭其写入视图/句柄后，该命名对象仍被读取器引用。只要游戏进程还活着且头格式没有损坏，旧版没有基于持续无进展的重探测路径；即使帧数据已经过期，也会继续持有旧对象。测试中随后以同名创建生产者，会得到此前被保留的对象。

第二项证明的是 Windows 对象与读取器生命周期问题，没有启动、结束或重启真实 RTSS，不能表述为已经实测了某个真实 RTSS 版本的重启行为。

## 实际修改

未找到槽位的全表查找改为最多每 1 秒重试一次。表布局改变（版本、表偏移、槽位大小或数量）会立即重新查找；已经定位且 PID 仍相符的槽位继续走原快速读取路径。

映射刚打开时有一个 5 秒重探测窗口。只有真正推进且具有有效帧时间的稳定 marker 才延长这一窗口；重复读取、缺槽位、busy、无效帧时间均不会无限续期。到期先解除自身映射引用，再通过原有一次/秒的打开退避重新探测。

新映射和新槽位仍需预热，只有随后新的真实 marker 才作为帧观测。没有给陈旧数据盖新时间，没有为 1% Low 估算值或续期。进程退出检查在这些预算之前，立即释放映射；不等待 1 秒重试或 5 秒映射窗口。

现有快速采样间隔、绘制时钟、历史长度、FPS/1% Low 的观测截止时间均保持本轮冻结源码。没有新线程、定时器、进程枚举、常驻日志或第二采集器；仍然使用 FILE_MAP_READ。

代价明确：表布局不变且尚未定位目标槽位时，新挂钩的发现最多会等待约 1 秒。正常已定位槽位的帧时间采样不因此变慢。这个预算只限制缺槽位的查找，不限制已经成立的帧数据读取。

## 验证

新 tools/monitor_rtss_probe_lifecycle_selftest.mjs 执行冻结/当前实际头文件。测试只在全表查找和槽位读取位置注入操作计数，并包装映射/进程打开 API 计数；不替换读取或判断逻辑。实际 Windows 独立命名映射、当前测试进程的真实创建时间及一个隐藏的专用短期子进程用于生命周期测试。没有接触真实 RTSS/HWiNFO/游戏映射。

- 冻结版本 62 项：包含对旧缺陷表现的明确期待，用于复现，不是说旧版已经修好。
- 当前版本 64 项：覆盖缺槽位、首次发现、布局/版本变化、连续出帧、重复 marker、冻结生产者、永久 busy、无效时长、缺映射、PID 创建时间错误、槽位移动、真实测试子进程退出与释放。
- 真实 Output 层一起执行，验证 RTSS 帧率/帧时间与独立 HWiNFO 1% Low 共存、重复 packet 不续期、Low 自身过期，以及 RTSS 过期时保留仍新鲜的 HWiNFO 后备。
- 现有 monitor_rtss_duplicate_read_selftest.cpp 的 3 项和 monitor_frame_output_receipt_selftest.cpp 的 4 项未修改、重新编译执行通过。前者对已安装官方 SDK 字段偏移的既有断言也重新执行。
