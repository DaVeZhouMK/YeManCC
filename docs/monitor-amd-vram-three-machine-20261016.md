# AMD 显存三方对照：Win5 / ROG Xbox 2025 / 本机已有样本（2026-10-16）

## 当前结论与未完成部分

**确认的是“已用容量已进入统一快照，而容量分母/百分比缺失，所选百分比项目因此自动隐藏”。尚未修复远端两台机器的显存百分比。**

不能把“GPU 已被识别”“读取到已用 MB”“可以计算占比”视为同一件事。也不能用本机被选中的 NVIDIA 独显显示正常，证明旁边 AMD 核显的数据完整。

本轮对照用户提供的两个归档及本机既有只读传感器/生产解析样本，没有采样本机硬件，没有安装程序、调用 Windows 容量接口、重启 YMCC/Steam/游戏或写入设备。

## 原始字段与槽位差异

本机既有行表中：

- AMD `iGPU [#1]: AMD Radeon` 的 `GPU Memory Usage` 单位是 MB，值 100；另有 `GPU D3D Memory Dedicated` 14.734375 MB 和 `GPU D3D Memory Dynamic` 34.13671875 MB。
- NVIDIA `dGPU [#0]` 另有 `GPU Memory Allocated`、`GPU Memory Available`（MB）和 `GPU Memory Usage`（%）。

同名 `GPU Memory Usage` 在两种槽位里单位不同。现有原生解析按单位分开读取，AMD 已用值没有漏进前端，也没有错误拿 GPU 使用率或显存控制器负载当容量占比。

334 条原始快照包含的是已处理的 top，**不包含远端完整原始 HWiNFO 行或远端 D3D 已用计数**。因此现有包不足以确认两台远端设备应当用哪一种已用口径配合哪一个容量分母。

本机 AMD 的显示模型对照是从已保存的原始 GPU 数值构造的隔离消费包；它不是本轮实时读数，也不是当时默认显示所选 GPU 的完整 top。NVIDIA 对照使用当时真实完整 top。`THREE-MACHINE-MODEL-RESULT.json` 明确保留两种证据范围。

## 为什么没有直接填入 Windows 容量

同包、同一进程的另一项容量设置诊断已有适配器项：

- Win5，10:15:20.123：`dedicatedBytes=8403652608`，约 7.83 GiB；含两个同名 8060S 适配器/LUID 项。
- ROG，10:06:13.669：`dedicatedBytes=6220378112`，约 5.79 GiB；也有两个同名适配器/LUID 项。

这属于此前已有请求返回的诊断，并非本轮新查询。两次能力请求的整体 `available=false`，原因分别为型号/接口身份校验未通过，不能把整体状态解释成没有显卡或没有容量信息。

Win5 这里的专用容量显著小于监控已用值，直接混合计算会超过 100%。ROG 即使数值落在范围内，也不能据此证明它和 `GPU Memory Usage` MB 是同一统计口径。两项观测时间不同，日志也不是整个系统的原子快照。本轮没有用系统内存、显存设置目标、历史最大值或另一张显卡的数据补分母。

## 已完成的源码改动

为了下一份日志能在现有统一数据链里直接辨别口径，补入有界的 `gpuMemoryEvidence`。它仅属于高频 `monitor-detail.log`，不进入 HUD 数据、控制数据或低频生命周期日志。

- 继续复用同一次 HWiNFO 解析遍历，记录选中 GPU 的槽位、传感器身份、已用来源、规范化为 MiB 后的原始容量元组，以及同槽位的 D3D dedicated/dynamic 已用计数。
- 不把 D3D 分配量作为物理显存总量，不改变 GPU 的功耗优先选择/会话固定规则。
- 原有高频详细日志门关闭时，不捕获额外 D3D 行、不分配诊断块；实际记录函数仍在缓存复制和 JSON 构造之前返回。
- 门开启时按现有采样预算记录。只在当前统一缓存采集时间仍与本轮对应时附带证据；缓存已被替换则记录明确省略原因。
- 单路记录继续受 32 KiB、队列 256 KiB/16 条、文件 2 MiB 加一份轮转约束。新示例证据约 535 字节，包含证据的代表完整记录约 2.8 KiB；最大名字转义也验证小于 2 KiB 证据预算。
- 诊断存储是按包申请的一块固定 64 项数据（计数载荷 1024 字节，另有共享所有权开销）；解析暂存最多 256 项、4096 字节，详细门关闭时不初始化该额外数组。没有无界队列或全局累计缓存。
- 分配失败、诊断回调失败不会改变监控主数据或使采集失败。GPU 主 Device 对象布局保持原样，普通解析关闭诊断后的堆分配计数为 0。

这一步补全下一次诊断所需的证据，**不等于已补齐容量或已完成百分比修复**。后续必须根据同槽位实际统计确认正确容量来源，仍由 YMCC 统一层提供，HUD 继续只消费。

- 新原生解析/真实记录函数测试 36 项通过：同槽位、双 GPU、防跨包、D3D-only 不产生 GPU、合法零、非法单位、上下界、诊断门、1 Hz 预算、字节上限、缓存替换、诊断分配/回调失败以及按需内存计数。
- 现有真实原生解析器/发布器 19 组，在冻结的旧头文件和当前头文件下分别编译运行，完整输出逐项相同。
- GPU 原生选择回归 17 组、GPU 消费端回归 14 组，未启用可选实时硬件读取。
- 现有详细日志边界 48 项；实际 IPC 路由 8 项和接线 12 项。
- 原生消费回归 8 组，包括解析、快照服务、脉冲；数据链路 31 项及类型检查通过。

初稿把两项诊断计数直接加入每个 GPU Device，GPU 大型离线夹具遇到默认栈溢出（`FIRST-GPU-BUILD.log`）。没有调大栈或放宽断言；改为只在详细门开启时分配一个有界、按包持有的诊断块，GPU Device 保持原大小。原夹具随后正常通过。

两个原有测试的源码接线标记因记录函数新参数、GPU 临时指针而更新；GPU 独立夹具补了关闭诊断门的替身。选择/数值断言没有放宽。
