# 监控原生推送传输优化

日期：2026-10-17。已合入主线源码，尚未链接、制包或部署。本轮没有修改前端数据读取接口、HWiNFO 或用户配置。

## 改动

之前 `monitorHudPulseTick()` 调用通用 `ipc_emit()`。这会把已经拥有的监控事件深复制成 enriched，再深复制进广播封装，并为每个 renderer 重复调用 JSON dump 和 UTF-8→UTF-16 转换。

现在监控专用的 `ipc_emit_monitor_hud_pulse(json data)` 移动这个本地事件进直接构造的封装。第一次发现有效 renderer 时才序列化与转换，后面的 renderer 共用同一个只读宽字符串。没有有效目标时不 dump，保持旧实现的错误边界。

事件名仍为 monitor.hudPulse，消息字段、目标窗口、目标查找与发送顺序一致。失败的 PostWebMessage 回执仍按原来方式处理，后续窗口继续发送。通用 IPC、power 事件派生与 gyro 专用路径均未修改，原有 UiCostIpcScope 事件计数入口保留。HWiNFO、RTSS、快照发布、200ms/1000ms 推送周期、nonce 租约和停止/过期规则不变。

## 完整生产函数验证

新增 `tools/monitor_pulse_transport_selftest.mjs/.cpp` 和精确旧发送函数夹具。测试编译完整旧 `ipc_emit` / `ipc_post_json`、实际 UTF8 转换函数与完整新专用发送函数，仅 WebView 目标为隔离替身。

- **3,841 项断言、416 组广播对照通过**。
- 检查无主窗口、仅子窗口、空/null/无 view 子项、多个 renderer、发送失败返回值；前一个窗口发送时关闭后续子窗口，后续目标仍按原顺序跳过。
- 对所有目标比较原始 UTF-16 消息字节、ID 与顺序，并用独立 canonical JSON 封装核对；覆盖中文、emoji、转义、嵌入 NUL、数字上限、空/非对象事件、无数据快照和大载荷。
- 非法 UTF-8 在有目标时同样严格报错且不发送半包；所有条目均无有效 view 时不进行序列化，维持原异常行为。
- 旧的源缓存与未交出所有权的 JSON 不会被移动或修改。
- 快照/租约回归：51,373 项断言、4,497 组响应、2,432 组推送效果，G3E/ROG/Win5/本机共 192 份真实快照回放通过。
- 禁止触发浏览器 timer 的后台时钟、主数据入口与两条 carrier 回归 10 个场景通过。
- 13 项快照路由/字节上限检查通过。
- 冻结完整 native/main.cpp 翻译单元编译成功，合入后 main.cpp 与已编译 main.cpp 字节一致。其后无关并行任务对 native/onex_x2_windows.h 有修改，已保留并单独记录；不能把本轮冻结编译说成这些后续编辑已验收。

## 分配与序列化工作量

以下均为预热后的 2,500 次完整发送，包含 sender 内临时对象销毁，不包含已拥有输入的准备或真实 COM/renderer 开销：

| 顶层载荷 | 有效 renderer 数 | 修改前分配次数 | 修改后 | dump / 转换次数（前→后） |
| --- | ---: | ---: | ---: | ---: |
| 小载荷 | 1 | 330,000 | 60,000 | 2,500 → 2,500 |
| 小载荷 | 2 | 357,500 | 60,000 | 5,000 → 2,500 |
| 小载荷 | 4 | 412,500 | 60,000 | 10,000 → 2,500 |
| 16,000 字节 top 文本 | 1 | 350,000 | 80,000 | 2,500 → 2,500 |
| 16,000 字节 top 文本 | 2 | 397,500 | 80,000 | 5,000 → 2,500 |
| 16,000 字节 top 文本 | 4 | 492,500 | 80,000 | 10,000 → 2,500 |

例如小载荷双窗口的分配请求为 38,465,000 → 10,512,500 字节；16,000 字节 top 的双窗口为 655,277,500 → 258,952,500 字节。每个窗口的投递次数完全相同。零目标时不增加工作，且省去事件名临时字符串的分配。

这些是传输函数内部的分配/序列化工作量，不能换算成整进程 CPU 百分比或驻留内存下降，也不是减少推送频率得到的收益。
