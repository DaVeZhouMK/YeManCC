# 监控 CPU 调用与数据边界查错 — 2026-10-15

本轮继续“挖穿监控 CPU 调用优化和数据 bug”的长期目标。已修改当前主线并完成下列定向验证；本报告是阶段记录，不把这些局部通过视为整个目标已完成。没有测量实际 CPU 百分比、启动已安装 YMCC/Steam/游戏或进行部署。

## 已复现并修复

### 1. 预览的失效时间与输出不一致

监控页原先从 top/fps 时间戳统一计算“加 6 秒”唤醒，遗漏了 FPS、1% Low、帧时间各自的观测期限。实际 Settings SFC 的修改前回放显示：曲线应在第 3 秒、Low 应在第 4 秒、FPS 应在第 5 秒失效，但仍保留到统一的下一次第 6 秒唤醒。现复用既有 createHudAgeLease，按统一投影生成的各通道期限老化，无新增读取或轮询；停用、KeepAlive 和卸载清理自己持有的订阅与计时器，TDP 使用当前实际写入回执。

### 2. FPS 期限变化被“值相等”过滤

sameHudData 原先比较 FPS 值、观测时间和目标，没有比较 FPS 家族共同依赖的期限。同值同观测、期限变化时，组件可能保留旧期限并提前隐藏。现仅在选择任一 FPS 家族字段时比较该期限；实际生产渲染器的修改前/后回放确认修复。仅选择硬件的消费者仍能去重，不凭缓存延长数据。

### 3. 每次绘制回执重复通知宿主

desktopHud.painted 在首次已确认后仍调用 changed，导致宿主反复检查输出可用性。现仅首次绘制或从未知状态恢复时报告状态转换。201 次实际 owner 数据帧和绘制回执中，changed 从 201 次变为 1 次，帧数仍为 201，关闭、身份、回执和数据需求保持原逻辑。

### 4. 输出关闭仍请求快速曲线模式

宿主启动和成功应用设置的路径缺少 enabled 判断。关闭监控但保留曲线开关时仍请求快速模式。现这两处与现有偏好更新路径一样，只在自定义监控开启且曲线启用时请求快速模式。实际 host 的三个处理器均用惰性内存端口回放，没有启动时钟或采集器。

### 5. Windows CPU 首帧/失败被混作真实 0%

已有唯一 Windows CPU 采样入口继续负责总占用与各核心。Deltas 现在附带 totalValid：首帧、计数回退、溢出、零间隔、拓扑变化、超过 6 秒的间隔以及部分核心无效时，不把部分合计当作整机有效占用；有效核心图块仍保留，真实 0% 仍为有效读数。GetSystemTimes 回退复用相同 delta 规则，API 失败与切换来源后重新建立基线，避免跨长暂停计算平均负载或无符号回绕。

原生统一发布增加可选 cpuUsageValid/cpuUsageTs，生产采样调用明确传入证明。既有消费者继续通过 monitorData 解析，沿用独立有效期和停止失效门；cpuUsage 数字与图形消费同一份读数。HWiNFO 不可用时，真实 Windows 占用可继续显示；Windows 过期时，不借用新硬件时间续命。旧发布者没有这两个字段时保留旧版规则。

### 6. 仅 FPS 需求仍读取 CPU 计数器

原采集循环即使 top=false 也调用完整 CPU 采样，但结果不会进入 top 包。现只在现有 top-demand 分支采样。提取真实修改前/后采集语句，注入 Windows API，200 次仅 FPS 迭代的 CPU 快照调用从 200 次降到 0 次。top-demand 仍每轮取一次，没有新建采集器。

### 7. 重复需求绕过退避与旧会话回执污染

触摸板任务按用户授权移交了两条监控发现。当前主线确实存在，已按最小 hunk 整合，并保留本轮 CPU 证明、解码缓存与其他并行修改：

- 同 owner 相同 top/fps 的 acquire 只替换订阅 token，不再用 intent 清零重试期限。同一时刻首次失败后重复 1,000 次，启动从 6 次降到 1 次；真正需求变化仍立即推进并恢复预算。
- 真实发布会话替换时增加控制代际，启停成功、拒绝和异常都核对发起代际。旧回执不会把新会话标成成功或写入新会话退避；首次学习会话号仍接纳初始命令。
