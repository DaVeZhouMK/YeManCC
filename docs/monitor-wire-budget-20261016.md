# 统一监控快照解析前的字节上限（2026-10-16）

本轮继续优化监控数据消费和异常情况下的 CPU 工作。生产修改只有 `src/bridge/monitorData.ts` 与新增的纯文本辅助模块 `src/bridge/monitorSnapshotBudget.ts`。没有新增硬件源、采集、读取循环、计时器或线程，没有安装、重启程序或进行游戏测试。

## 发现的问题

原生发布端已有 top 16 KiB、FPS 16 KiB、两路合计 24 KiB 的文档字节上限。前端解码器的 65536 字符限制仅决定是否缓存，并不阻止更大的原文进入 `JSON.parse`。

因此大文档或多字节文本仍会在前端被解析，甚至被当成有效可用快照推进会话/序号。修改前夹具实际复现了 1 MiB top、1 MiB FPS、中文/emoji 单路超限和两路合计超限；若这些文档携带另一个会话号，旧入口还会接收该号并退休原会话。

## 修正

- 在统一 hub 的 `normalizeSnapshot()` 内，先通过原有 schema、available 和 collectedAt 检查，再执行字节上限，之后才允许进入 top/FPS 内层 JSON 解析和生命周期接纳。
- 单路 16 KiB、合计 24 KiB，与实际原生头文件常量进行测试比对。上限针对内层 top/FPS JSON 文档的 UTF-8 字节，不是 UTF-16 字符数，也不是整个 IPC 消息或进程堆内存上限。
- 超限的 `available=true` 快照不解析，不推进 session/generation/seq，不确认活跃标志或待启动命令；拦截动作不触发额外重试，读取本身原有的正常退避推进不变。下一份正常包可继续使用原会话。
- `available=false` 的既有失效通知仍然立即生效；被忽略的载荷不扫描、不解析。
- 不截断 JSON，不把缺失数据伪装成 0。不改变原来的采集频率、值、来源、新鲜度和正常包解析规则。
- 旧原生四文件兼容通路保留原有每路最多 8192 字节的读取约束，本轮未改它的采集或降级策略。

## 低 CPU 路径

常规小文档只通过长度上下界判断。UTF-8 每个 UTF-16 码元至少 1 字节、最多 3 字节；能由上下界确定的文档无需逐字扫描或建立编码缓冲。

需要精确计数时，直接读取码元，正确处理中文、emoji 代理对和孤立代理项，并在超限时提前停止；不分配 TextEncoder 字节数组。

每个 hub 只记住上一组经过容量检查的大文本及其字节数。相同原文复用计数结果；拒绝的超限原文不替换已有缓存。这里缓存的是不可变文本的体积，不是测量值、时间或有效期。

确定性计数结果：

- 80 次普通小快照：UTF-8 扫描 0 次；top/FPS 各解析 1 次。
- 80 次相同的大快照：两路合计精确扫描 2 次；top/FPS 各解析 1 次。
- 超限文档及后续正常恢复组合：修正后 top/FPS 内层解析 0 次，保留已有正常解码缓存；旧版会解析超限原文，并在恢复时重新解析原来的内容。
- 重复包不更新原始观察时间；越过截止时间后，CPU 功耗和 FPS 仍失效。

这些是工作次数与容量边界证据，不代表整机 CPU 降幅；没有运行 CPU 百分比压测。
