# 开机模式预设与当前运行配置隔离（2026-10-27）

用户约定：已保存的开机模式预设不会自动吸收当前运行配置。模式 1 保存为关闭虚拟手柄后，临时启用 SteamDeck，或使用其他开机模式，再选择模式 1，其下次开机偏好仍为关闭。修改预设需要在编辑器明确保存；选择开机模式本身即提交该模式已保存的内容，无需额外保存。

## 原因与修复

`src/bridge/bootModes.ts` 原有 `reconcileBootModeSnapshot` 会在编辑器快速读取和完整读取时，将当前运行状态同步进全局模板或当前场景覆盖。即使没有编辑虚拟手柄，只重新打开编辑器再保存其他字段，也可能把 SD 带回模式 1。

移除这段自动回写及两处调用。已有预设从持久化文档读取，当前设备读取继续服务于能力检查和启动应用的比较。`activeSnapshot` 继续表示实际应用记录，不因浏览页面而改变。仅初次创建缺失的文档沿用原有配置采集；已有自定义预设不自动恢复出厂值。

此规则覆盖全局模板、继承全局的模块和独立场景覆盖。模式 2 继续默认跟随全局，模式 3／4 继续初始推荐 SteamDeck，用户明确保存的自定义始终有效。

## 四模式正反向复核（2026-10-27，用户进一步澄清）

严格区分预设、下次开机选择和当前运行状态。模式 4 已实际应用 SD 也不能覆盖模式 1 的 OFF；只有在编辑器修改对应模式并保存，才替换预设。原有明确选择的“跟随全局”关系保持有效，运行状态不作为新的预设来源。

补查发现：虽然已移除 `reconcileBootModeSnapshot`，`normalizeBootModeDocument` 仍会用实时采集结果递归补齐已保存全局模块的缺项。实际执行模式 4 → 模式 1 后，运行时的 performance 版本字段，以及旧预设未保存的 input ownership／gyro calibration，也可能渗入预设。

已保存模块现在以清洗后的持久化值为准，不再递归合并实时字段。`activeSnapshot` 继续单独记录实际应用情况，初次创建新文档及缺失整个模块的旧文档兼容路径保留。旧输入模块缺少 ownership 时，运行配置补丁省略该项，避免写入 undefined 导致配置哈希失败；不会为修复哈希而把实时值补进预设。

正向链路：编辑器按模式保存 → 选择开机模式 → `syncStartupInput` 写下次开机偏好 → 原生新 Windows 启动消费偏好 → 前端用已保存模式解析完整配置。实时采集仅作设备能力和应用差异比较，已保存模块不因此变化。

反向核查：最终手柄输出追溯到所选模式解析的 input.persona；下次开机偏好来自 boot 指向的预设，编辑保存其他模式不会改用那个模式；`current`／`activeSnapshot` 是实际应用记录，不作为既有预设的回填来源。普通手柄页改变的是运行配置；打开、收回编辑器、浏览模式和同次 Windows 启动内重开，不会修改模板。

沿用原两个测试 ID、128 项运行时断言、80 个文件 UI 场景及原预算。现有断言增加完整模式 4 SD → 模式 1 OFF 应用、四模式分别显式编辑保存、完整／缺少可选字段的既有模块隔离；原 UI 场景补查所有转换的启动前后模板完全一致。复核原件和最终状态见 `G:/YeManCC-Work/Testing/YMCC/Evidence/BootMode-PresetIsolation-20261027/strict-four-modes/RESULT.json` 与同目录 `REPORT.md`。各次失败原件保留，不把模拟启动当作真实重启验收。
