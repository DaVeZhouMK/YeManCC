# 统一监控读取原始快照交接与复制优化（2026-10-16）

本轮去掉上一轮为显示/控制隔离增加的正常读取复制。显示端消费本次读取已经存在的原始快照，控制端仍得到原来那份独立、可修改的副本。生产修改仅 monitorData.ts；没有新硬件源、采集入口、轮询、线程、定时器或 native 命令，没有部署、重启或现场游戏操作。

## 方案与所有权

公开 createMonitorDataHub 和 read() 的参数/返回接口保持原样。内部增加不导出的生产 owner 工厂：在现有 hub 完成解析、生命周期与停止边界处理后，原来的 structuredClone 仍为每位控制读者生成独立副本，同时用模块私有 WeakMap 关联这份副本与本次真实原始快照。

readMonitorSnapshot 取得副本后立即取出并删除关联。若期间没有更新的发布获胜，就将原始快照交给已有只读显示边界；控制副本照常返回。没有按 seq、对象字段摘要或时间窗口猜测复用旧数据，不增加逐字段/数组比较或 JSON 签名。私有关联不是新数据源，也不修改观察时间/有效期。

关联只存在于读取交接期间，在控制结果返回之前删除；迟到读取和回调中更新发布的分支同样删除。没有历史列表或额外清理 timer。新增测试中每次返回及最终收尾的待交接计数均为 0；这是确定性生命周期计数，不是整进程堆内存测量。

同一在途请求的多个读者仍共享原始结果，每人得到自己的控制副本。第一位读者把私有原始结果封装为只读显示对象后，后续读者仍可正常 structuredClone 出可修改副本。解码模板的外层对象不共享，不会因冻结本次结果而冻结后续新样本。

若未来异常分支缺少私有关联，仍使用上一轮的隔离复制回退；没有因为省复制就把控制对象直接发布。通过故障注入验证该回退。带对象型旧 FPS 元数据仍保留原形状、控制/显示对象分离，并沿用不授予选择器缓存资格的规则。

## 实际模块的确定性计数

修改前基线为上一轮已完成显示隔离的实际源码。完整 fixture 包含 128 个核心值、128 个标签与 120 个真实帧时间点。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 一次普通读取：整快照复制 | 2 | 1 |
| 200 次顺序读取：整快照复制 | 400 | 200 |
| 同批读取：被复制的数组项合计 | 150,400 | 75,200 |
| 两个并发读者：整快照复制 | 4 | 2 |

| 两个并发读者：实际快照请求 | 1 | 1 |

| 200 次高频推送：整快照复制/交接关联 | 0 / 0 | 0 / 0 |

普通顺序读取次数没有增加。高频 native 推送继续直接消费已有结果，与读取交接机制分开，没有新增 clone、关联或命令。新增 WeakMap 交接和固定函数调用也有工作量；上述次数不等于完整链路 CPU 指令、内存字节或整机 CPU 降幅，没有执行 CPU 百分比压测。
