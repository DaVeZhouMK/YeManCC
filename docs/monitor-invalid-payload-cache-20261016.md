# 监控重复无效载荷的解析优化（2026-10-16）

本轮移除统一监控消费者对相同无效文本的重复解析工作。生产修改只有 `src/bridge/monitorPayloadDecoder.ts` 和 `src/bridge/monitorData.ts` 的两个启用选项。仍只消费 YMCC 统一快照，没有新硬件源、读取循环、线程、定时器或刷新周期。

## 修改前证据

实际打包修改前生产 hub/parser，用同一份 8,027 字节的损坏 top JSON 连续读取 200 次：全部正确返回 null，但 parseTopPayload 仍执行 200 次。无效输入不建立会话，这是原有正确行为；本轮优化其重复失败成本。

其余两类也存在同样工作：损坏 FPS JSON，以及能通过 JSON.parse 但结构/关键读数无效的文档。原解码器每次失败都清空唯一模板，下一次相同文本又进入解析。

## 修正与边界

- 只有现有 top/FPS 两个纯文本解析器显式开启 `cacheInvalid`。这些解析器返回 null 只由输入文本决定，不读取时间、设备或文件。
- 相同坏文本占用原有单槽，返回 null 时不再进入解析器。下一个不同文本立即重新解析，没有 TTL、等待或失败恢复延迟。
- 成功模板和失败文本共用原有槽位，切换时替换/清空，未增加历史 Map、数组或每包对象。
- 失败文本单槽最多 16,384 个 UTF-16 码元。这是解码器保留长度上限，不能当作 UTF-8 字节计数或 JS 堆总量。
- 生产入口仍先执行 top/FPS 各 16 KiB、合计 24 KiB 的 UTF-8 字节检查，再调用解析器。因此大包不会借失败缓存绕过字节门槛。旧文件通路保留原来的单路 8 KiB 读取限制。
- 公共 helper 默认不启用失败缓存，保留可能依赖外部状态的调用方语义；解析器抛出的异常仍不缓存；cacheable=false 的有效特殊结构继续不缓存。
- 返回成功值仍按原规则隔离复制；不缓存部分成功快照，不推进无效包的 session/generation/seq，不把缺失读数变成零。

## 实际工作计数

| 相同输入重复 200 次 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 损坏 top 的解析次数 | 200 | 1 |
| 结构无效 top 的解析次数 | 200 | 1 |
| 损坏 FPS 的解析次数 | 200 | 1 |
| 结构无效 FPS 的解析次数 | 200 | 1 |
| 正常读取的 top/FPS 解析次数 | 各 1 | 各 1 |
| 正常读取的控制副本数 | 200 | 200 |
| 正常高频推送的控制副本数 | 0 | 0 |

另以 2,000 份混合数据逐份比较完整 hub 归一化结果与 HUD 投影：字段、身份、数组和拒绝语义全部相同；top+FPS 解析次数从 1,182 次变成 462 次。交替变化的坏文本仍会逐次解析，不为降低计数而跳过新输入。

这只证明具体重复工作减少，不等于实测 CPU 百分比或游戏帧率改善。正常路径增加一个布尔状态/条件检查；失败槽保留一份有界文本，不声称零开销。
