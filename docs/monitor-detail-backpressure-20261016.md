# 监控详细快照队列压力与恢复优化（2026-10-16）

本轮继续优化数据与重复 CPU 工作，生产修改只在 native/monitor_detail_log.h 的 Queue::permit。持续优化目标保持进行中。

## 已复现的问题

1. 满队列仍发放编码许可。主程序在取得许可后才复制统一缓存、构造 JSON 并调用 offer；offer 再因队列上限拒绝。这使后台写入停滞期间的大部分快照复制和编码成为无效工作。
2. 后台池连续拒绝任务可把诊断队列填满并留在未排程状态。之后 offer 因队列已满提前返回，无法再尝试调度；即使后台池恢复，也没有排空机会，直到其他收尾动作介入。

## 修正

在原 1 秒节流预算取得后，先用已有原子计数检查行数/字节容量是否已满。已满时计入 droppedQueueFull，并在复制/编码前返回无许可。同时使用原有 kick 尝试恢复一个此前未能排程的 drain。检查仍消耗本次 1 秒预算，因此频繁调用不能制造密集调度重试。

这只是诊断的压力控制，不改变监控数据采集和显示。offer 内原有的严格容量、代际、门状态与 try_lock 检查继续保留，覆盖检查后发生的竞争和实际字符串容量。正在写盘的记录仍计入预算；写盘阻塞不会让生产者等待 writer 锁。

原限制不变：单条 32 KiB，待写负载 256 KiB/16 条（含在途写入），单文件 2 MiB、仅一份备份。快照只进入现有详细日志通道，关闭详细日志不因压力检查产生编码或重试；没有新增计时器、线程、硬件读取或日志入口。

## 证据

真实生产头文件修复前/后 A/B 编译，只有命名空间和 JSON include 路径为隔离而调整。

- 合成队列最多保留 3 条，后台不执行，100 次每秒采集机会：修复前统一缓存复制/JSON 编码各 100 次，修复后各 3 次；两版真正保留的 3 条记录逐字节一致，97 次放弃有计数。
- 连续任务拒绝填满队列后恢复后台：旧版保持未排程，新版在后续现有采集节拍重新调度并排空，之后新记录恢复写入。
- 100 次高频满队列调用只增加一次符合 1 Hz 的调度尝试；字节预算、行数预算、门关闭/重开和后台写盘阻塞均有反例。

这些是确定性的工作次数与队列恢复证据，不能换算成整机 CPU 占用或游戏 FPS 提升。没有运行 CPU 占用压测。
