# 模拟测试：场景工作消耗与GPU能力库

2026-10-17。主线入口：`public/performance-simulation/index.html`。

## 唯一数据链路

GPU能力数据集中在 `gpu-capability-library.js`，TS显卡分、游戏GPU服务量、三组对比、快速模拟和图像读取同一个只读能力库。正式硬件调度器没有增加第二份浮动TDP控制代码。

左侧保持AI场景预览、场景选择与同步表格，底部顺序为FPS、能效变化、TS功耗曲线。TS图使用瓦数横轴，显示原版CPU/GPU两条基线，以及当前自动或手动设置下的CPU/GPU两条优化线。虚线表示原版，实线表示优化方案；它不是时间走势。调节参数会重算优化线，纯粹经过时间不会改变曲线。选择原版预览时保留最后选择的优化方案，仍可比较四条线。

曲线统一从3W开始，包括258V；395在13W以下没有可用点，3–13W区域保持无数据。3–35W每格1W，35W以上每格5W。上限跟随机型，Steam Deck为16W，常规模型45W，G3E/395延伸至80W。没有编辑入口或本地曲线覆盖导入。

`ts-power-curve.js`是只读取样器，不运行或写入第二个TDP调度器。四条线均调用实际CPU/GPU供给函数，使用相同场景、相同非突发参考时刻与双侧就绪状态。原版沿用原版控制参数，优化线沿用当前自动/手动控制参数；不再给图表单独套GPU供给比或第二次优化倍率。只读能力库的原始锚点另存于取样结果的`stock.rawGpu`，不等同于经过CPU共享功耗分配后的供给分数。Steam Deck16W1400GPU分上限保留。CPU/GPU曲线不是两个子测试同时满载的实测电源轨功耗，也不直接乘到最终游戏FPS上。

## 优化曲线：CPU压制换取GPU收益

`optimization-curve.js`保留当前CPU提交、GPU消耗和共享TDP分配链路，增加用户指定的“优化曲线 / GPU优化幅度”：3W=3%、20W=20%、30W=5%、43W=0%。相邻点连续线性插值，例如24W=14%；43W及以上为0，3W以下无此曲线数据。

该曲线表示压制CPU后可获得的GPU最大增益，不按原版、自动或手动标签直接加成。实际增益先受当前GPU可行能力限制，再乘激活比例：CPU能力下降比例除以20%，以及CPU释放功率比例除以20%，两者各限制在0–1后取较小值。两项20%是显式工程标定参数，来源不是硬件通用定律。CPU参考功率与实际功率均以相同TDP、相同优先级、相同活跃条件经过同一分配器求解，避免把空闲或预算外功率当作CPU释放。

CPU成本已由现有频率、电压、功耗和CPU供给分数体现，优化模块不再扣第二次CPU分。增益作用在实际GPU服务能力上，经过CPU提交队列与GPU完成帧计算影响FPS和1% Low，不能直接乘最终FPS。CPU过低时依然会喂不饱GPU，不能以GPU分提升抵消CPU饥饿。Steam Deck1400分上限继续生效，原TS能力库和只读图像锚点保留；旧的额外GPU频率交换倍率已移除，防止重复加成。浮动TDP按当前下发上限读取曲线，不误用全局最大值。

这是一条按用户测试方向设定的模拟标定曲线，不表示每台APU、每个游戏必然有相同提升。诊断会记录CPU释放瓦数、CPU保留比例、GPU增益和来源，供回归核验。

瓦数标签按实际渲染字符边界保留至少12px间距；空间不足省略中间标签。左侧缩放后的实际像素边界也要检查，端点不能被SVG裁切。

## 增加TDP不能让原版与优化一起倒退

本轮修正覆盖供给计算、实际完成帧和TS图，不能只将画出的曲线抹平。错误有三处：GPU硬件可用功耗错用30W参考点而非机型上限；优化百分比退坡被当成绝对性能扣减；图表又额外应用GPU供给比例。

CPU功耗仍使用原参考功率建模，GPU可用功耗则按设备最大有效范围计算。GPU可行能力由只读曲线与用户优化曲线推导：

- 设原始供给曲线为R(u)，用户给出的最大优化幅度为g(u)，公式中按小数表示。
- 当前等效GPU供给瓦数q的能力包络E(q)=max[R(u)×(1+g(u))，u不高于q]，并受机型GPU上限限制。
- 当前包功耗w的原版参考S=max[R(q)，E(q)/(1+g(w))]。优化余量随瓦数减小时，参考性能追上包络，绝对性能不因余量退坡被扣减。
- CPU实际能力及活跃功耗释放共同得到a（0–1）。实际GPU供给=S+a×(E−S)，上限不超过E；这等价于在原版参考与可行优化能力之间插值。

最后一步避免“先乘最大幅度再截断、后来再减小倍率”造成的二次倒退。没有CPU释放时a=0，不能凭模式名字获得额外奖励；CPU过低仍会影响提交和游戏帧数。固定场景与固定CPU控制参数的比较覆盖全部整数瓦数；自动核心策略在阈值处切换属于控制参数变化，不能混作同参数的TDP比较。

包络只由当前参数与不可变机型曲线计算，不记忆用户先前跑过的最高分，不修改原始测试锚点，不虚构散热衰减。线性区间乘积可能有内部极值，因此包络同时检查原始数据点、优化曲线拐点及区间内极值，缓存按只读能力库和机型隔离。请求顺序不会影响结果。

## TS显卡分到游戏GPU供给的独立折算

本轮按机型新增只读的GAME_GPU_EFFICIENCY标定表。258V的普通3D场景使用3682÷4118=0.8941233608547838，即保留89.41%、减弱10.59%。两个参考数分别来自用户本轮确认的Z2E3682GPU分和既有258V30W4118GPU参考。这个数值是为了满足用户“TS较高、普通3D游戏与Z2E接近”的模拟目标，不是独立实测得到的Intel统一折损。

仅游戏GPU服务量乘该系数，TS显卡分、TS总分与CPU供给不直接乘系数。实际CPU调度需求仍会随游戏GPU速度变化，以免CPU继续为不存在的GPU帧数请求功率。第一人称、大型3A、轻度3D均为89.41%；大型二游与轻度2D为100%，保留用户要求的场景差异和低负载特性。G3E、155H、1195等沿用各自既有标定，不能将258V的10.59%当作全Intel实测数据。

旧大型3A路径曾将258V某笔记本功耗不明的19.9FPS记录除以独立TS锚点，得到约0.6295355；Z2E没有相同折减。该记录保留为资料，停止作为258V掌机与Z2E同瓦比较的乘数。游戏GPU系数由同一供给链路应用一次，原版、自动、手动共用；CPU不足、有限任务、分辨率、呈现上限仍独立工作，不能将最终FPS直接锁成相同。

完整48秒场景循环与两个分辨率结果见performance-simulation-game-gpu-efficiency-20261017.md。同步对比中的GPU分数提示同时列出TS、游戏折算百分比与游戏等效供给，便于区分。

## 机型封顶与超额设定隔离

机型完整表见`performance-simulation-device-limits.md`。Steam Deck模拟有效上限16W；G3E与395为80W；其他8款为45W。设定150W可以继续保存在模拟临时参数中，但模拟有效预算先取设定值与机型上限的较小值，随后才运行浮动控制、核心分界和CPU/GPU供给。自动浮动的相对降幅也按有效上限换算；例如设定150W、降幅30%的45W机型，使用45W及31.5W目标。

原版、自动和手动的运行控制统一封顶；初始化、动态修改与核心阈值均使用同一有效瓦数。快照powerLimits记录设定、有效、最大和是否封顶，不能将模拟上限回写到正式硬件设置。51组封顶对比覆盖超过1W/150W、无浮动/中幅/激进、核心分界等于机型上限及运行中修改；另覆盖11机型×5场景的供给封顶。

## 右侧铺满实际高度，再适配左侧

432×628是右侧组件的设计基准，不是固定的屏幕高度。可用高度为实际视口高度减92px（顶部58、底部34），右侧局部比例为`(height-92)/628`，宽度为`432×比例`。控件、间距、字号一起等比变化，右侧底边始终落在视口底部34px处。没有改全局UI缩放。

宿主用ResizeObserver测量右侧实际边界，经同源消息传给`split-layout.js`。左侧先扣掉右侧宽度及间距，再用剩余宽高独立计算比例，不能继续按照旧窗口宽度绘制。其逻辑高度按剩余实际高度换算，因此预览、表格和底部三图保持对齐并占满可用区域。1280×720、1280×800、1160px宽及1536×1024、1920×1080高窗口均验证，另复现125%显示比例的原生截图大小。

右侧浮动下拉菜单从触发器所属编辑区读取局部比例，不能套用App其他页面的全局比例；供电状态仍按顶部固定坐标显示。实际渲染几何用于手柄上下左右导航、滑块和下拉菜单定位。TDP提示始终预留一行，出现提示不挪动参数。

轻度2D的demandScale设为1.8，CPU逻辑、CPU提交和GPU每帧工作量均比上一版增加80%。转场、AI、特效任务的有限工作包使用同一场景基础值，因此同步增加80%，不通过延长固定卡顿时段实现。分辨率规则、三策略公平工作量和机型能力保持；实际TDP仍由完成工作及共享上限计算，不能将显示瓦数直接乘1.8。

## 每帧如何产生

`场景CPU逻辑 → CPU渲染提交 → 已提交帧队列 → GPU渲染 → 帧率上限控制 → 完成帧统计`。

`frame-pipeline.js`执行连续工作积分，在CPU/GPU任务完成、提交完成、GPU完成和呈现时间点处分段。CPU与GPU可重叠工作；CPU尚未提交的帧不能进入GPU。最多缓冲2帧，帧数只在GPU完成并呈现后增加。CPU不足会耗尽已提交队列，之后GPU等待CPU；CPU足够后，进一步提高CPU能力不会继续改善GPU喂给比例。

CPU跑分中已包含频率作用，内部不再重复乘一次主频比例。实际时钟由频率上限、最低性能请求、睿频上限、积极性响应及共享功率约束共同决定。突发CPU任务会提高调度请求，但不能越过硬上限。

同一个总TDP预算在CPU和GPU之间分配。有余量时满足未满足的一侧请求，存在竞争时优先级参与分配；分配不足会降低实际CPU供给频率或GPU曲线上的等效供给点，不能只更改显示瓦数而维持原性能。CPU/GPU占用率来自实际忙碌时间，TS读数取最近窗口忙碌期间的供给平均，避免GPU空闲相位导致显示分数突跳。

原来的按预测FPS直接推进帧、最低任务切片、GPU占用反推功耗求解器和随瓦数按目标游戏FPS反推校准系数的旧路径已去除。尤其最后一种反算会抵消曲线显示。场景校准现在固定在未编辑的参考能力上，不随当前曲线值或TDP反向变化。

## 突发与分辨率

AI、资源准备、特效均生成一次有限任务，三种策略收到相同工作量。CPU任务完成后，与其相关的GPU任务才就绪。任务处理完即结束；动画长度不是强制掉帧时间。

突发总需求系数保留0.7，即用户要求降低30%。参考工作量使用60帧×0.08秒的工程归一，不能说成某个游戏的精确实测毫秒。AI只增加CPU任务，不乘分辨率；特效GPU任务按像素比例变化：720P为1080P的4/9。常态场景含几何工作与像素工作两部分，不把全部GPU工作都当成像素填充。

- RyzenAdj项目实现：STAPM、快慢PPT、温度/电流等限制并存。https://github.com/FlyGoat/RyzenAdj

本轮微软页面访问超时，未将超时结果当作新证据。Intel网页部分访问失败，不据此补造“Intel一定怎样”的结论。

GPU基准动态功耗占比0.88、CPU提交工作份额、归一化电压曲线、各类合成任务成本均为明确列出的工程代理参数。TS分和TDP不足以唯一解出真实CPU/GPU电源轨功耗。AMD较倾向使用CPU余量、Intel/Deck较倾向满足需求后收手的路线是用户观察的模型分支，不能推广为全部Windows设备的厂商保证。跑不满TDP还可能来自锁帧、设备本身的性能/频率/带宽上限等约束，不能统一填充到最大瓦数。
