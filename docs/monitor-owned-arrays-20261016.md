# 监控快照只读数组复用与回归核对（2026-10-16）

本轮继续处理高频统一快照在显示侧的重复工作。监控继续消费 YMCC 唯一数据层，没有新增硬件源、HWiNFO 读取、采集线程、轮询或定时器；没有安装、重启或实机游戏验收。

## 高频通道和容量

本轮重新运行了高频路由及边界检查。monitor.snapshot / monitor.hudPulse 仍走统一缓存；RTSS 快速区只在真实帧推进后发布。诊断进入 monitor-detail.log 高频域，先经现有门控和采样预算，再交给现有异步池；不写入低频生命周期流，100ms 快速分支不录制诊断快照。

容量保持：top 与 FPS JSON 文档各 16 KiB，二者合计 24 KiB。原生内存发布、快速组合提交、兼容文件提交以及前端解析前均有检查。超限整路拒绝，不截断 JSON；缓存组合超限时保留 FPS、放弃 top。拒绝的前端包不推进会话/序号，也不续期。

诊断原文总量最多 12 KiB，单条含换行最多 32 KiB，队列最多 256 KiB / 16 条，文件最多 2 MiB 加一份轮转备份。诊断仍最多每秒取样一次；这是日志预算，与快速数据通道分别控制。上述文档字节界限不是整个 IPC 信封或进程堆内存上限。

## 本轮生产修改

monitorCoreTiles.ts 与 monitorFrameTime.ts 在已有统一 JSON 入口为自己生成的普通稠密数组建立私有所有权标记：验证、复制并冻结一次后，同一不可变数组经过 HUD 模型和输出边界时可直接复用。

外部数组不会被打标或冻结。外部 Object.freeze 不能证明数值恒定：getter 仍可返回变化值。因此核心图块缓存只接受自己生成的数组，外部冻结 getter 仍会被重读；缓存图块结果本身也被冻结，防止调用者修改共享结果。复现负例先返回 20 后改为 80，修改前缓存错误保留 20，修改后返回 80。

核心原始数组最多 128 项，显示仍最多 16 图块；帧历史最多 120 点。来源、PID、时间/截止时间和最后一点一致性检查保留。外部 HUD 数据仍使用原来的前 120 项/非负归一化，外部 presented 历史仍使用后 120 项/有效帧时长规则，不混用两个边界。

monitorData.ts 仅在原解析点使用这个归一化入口；monitorHudModel.ts 在原输出边界复用已确认数组。hub.read() 返回的可变副本隔离行为仍通过回归。

- 热路径：10 组逻辑 + 11 浏览器场景，包含 1800 次异常元数据接纳、真实 output entry 的合成 IPC 更新及过期关闭。
- 核心消费：12 项；核心浏览器：8 组、84 个布局组合。
- 数据链路：31 项；生命周期：13 项，最后定时器为 0。

## 历史测试及证据修正

热路径测试原先与 2026-10-14 模型比较，已经包含不同的电池证明、进程身份和数组冻结约定。本轮改为本轮修改前冻结基线，保留旧脚本和旧失败。双方已有的解码次数、16 图块读取数、输出入口定时器数相同，不把过去的优化当成本轮新增收益。脚本中的 200 → 8 次定时器参考比较是独立朴素参考；实际 before/after output entry 都是 7 次。

原重复载荷测试的 frametime=8.3 与历史末点 11 不一致，历史实际被拒绝为空；原来的引用共享断言不能证明完整曲线共享。本轮改为末点 11，追加长度 120、publisher 身份和冻结结果断言；原脚本保留。

原 monitor_frame_time_selftest.mjs 本轮仍失败：34 个原生场景中只有“producer backwards resets”未通过，后面的浏览器段未执行。现有原生逻辑明确拒绝早于 hardwareAt_ 的采样，故不能期待旧采样替换历史。原脚本未改，失败 JSON 保留。隔离重放只替换该旧断言为三个检查：倒退时不能发布未来观察、正常时钟下原值/历史保持、原截止时间不能续期。相同模型部分 9 组和原生部分 36 场景通过。这个重放不包括原测试浏览器段，也不把原整套测试标成通过。重放首次编译的测试声明遗漏 auto，已在测试工件内修正，无生产修改。
