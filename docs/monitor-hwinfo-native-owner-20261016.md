# HWiNFO 管理迁回 YMCC 原生本体（2026-10-16）

配置、启动、停止确认、共享内存恢复和持续停更后的拉起，现由 YMCC 原生本体执行。没有新增生产助手 EXE、服务、采集线程或监控入口。数据仍由原有统一采集者和有界快照提供。

## 运行形态

自动恢复由既有监控判定触发，投递到现有 IPC 工作线程池，硬件采集循环继续运行。新增 `monitor.hwinfo.manage` 原生 IPC；其在全部异步设置模式中都离开 UI 线程执行。应用内原子占用位与原有 `Global\YeManCC_HWiNFO_Recovery` 互斥分别处理本实例重入和跨进程并发。

同一份 `YeManCC.exe` 支持精确的 `--hwinfo-manage start|restart` 命令模式，在界面、设备初始化与单实例检查前处理，完成后退出。需要权限交接时仍调用同一程序，等待本次返回的精确进程句柄，最多 60 秒，不等待 HWiNFO 的长期进程树，也不在超时后杀死已启动进程。主程序当前清单要求管理员；本机通过这一正常启动权限路径完成测试。

`PowerControl/YeManHWiNFO.bat` 仅作兼容转发，使用 Windows `start /wait` 调用同一程序，保留模式与固定周期白名单、真实退出码和含空格路径。旧 PS1 文件暂留作历史回退与对照，但生产原生管理和 BAT 都不依赖它。导出安装检查不再把这两个外部入口作为 HWiNFO 核心运行的必需文件。

## 保持的配置与健康规则

- 用户提供的稳定后台模板已内嵌于 `native/monitor_hwinfo_config.h`。恢复不依赖 `HWiNFO64/YeMan/HWiNFO64.INI` 这个本地文件。外部原始模板未改。
- 同一统一配置中的受管选择仅在配置事务中读取，不进入日常采样。PresentMon 固定保留；没有新增公开或自动 AMD SnapshotPolling 开关。继续保留 `NvClockMeasuring=0`、`USBC_PD=0` 与原有已验证上游策略。
- 保留其他用户节、字段、编码、换行、有效 1–3 秒周期；显式重启可以应用 1000／1500／2000／3000ms。健康的普通 start 不改配置、不重启；带显式周期的健康 start 返回 12，等待调用方明确重启。
- INI 读写上限 256KiB、8192 行；统一配置读取上限 16MiB。停止前预检，停止后重新合并。确认生产者全部退出后才配置与重新启动。
- 保留首次与上次备份，使用同目录暂存、原子替换与提交后逐字节核对；锁定文件拒绝替换，不覆盖并发外部值。
- 传感器优化只对固定已验证的 HWiNFO 8.54 图像 SHA-256 生效。只处理原来的 65 个磁盘／C-state／重复 RTSS 组，保留首次与上次注册表状态回执、回滚及并发值保护；不处理 PresentMon 组。未知图像保留原采集。
- 共享健康探测只读已有映射，保留原有签名、布局、行数、32MiB 行区、生产者年龄和前后头一致性规则。启动成功必须证明同一布局的生产者时间继续推进，不以“进程存在”或“共享区能打开”当作成功。
- 唤醒 3 秒等待、额外至少 15 秒的持续停更保护、一次故障一次恢复布防均保留。

## 实测抓到并修正的问题

首轮本机测试发现两处迁移错误，保留失败证据，没有把它记为通过：

1. 健康检查误按“请求的新周期”判断，导致健康 start 带 1500ms 时误触发重启。改为独立的一般健康检查，之后才返回周期延后状态。类型接口也移除了该健康判断的周期参数。
2. 直接 `CreateProcess` 启动 HWiNFO 返回 Win32 740。本机上游 EXE 清单同时具有 `requireAdministrator` 和 `uiAccess=true`。改为与旧启动方式对应的 `ShellExecuteEx`，保留隐藏窗口与精确进程句柄。首轮故障后曾用先前验证的旧脚本恢复一次 HWiNFO 和原周期；这一次明确不计入原生迁移验收。随后本体启动与恢复均重新测试成功。

收尾检查还拒绝了 IPC 中被隐式截断的浮点周期（例如 1500.1），并将互斥忙／需重启应用周期记录为延后，而不是硬件失败。

## 本机生命周期

已备份后部署原生程序和 BAT。前端、游戏、Steam 和用户设置没有因此改写。实际运行 Cyberpunk 2077；游戏原进程 PID 43508 一直保留。

| 项目 | 实机结果 |
| --- | --- |
| 健康启动 | 连续 3 次 start 返回 0，HWiNFO PID 与 INI 不变 |
| 健康 start 请求不同周期 | 返回 12，不改 PID／INI |
| 显式周期重启 | 本体返回 0；共享区真实周期从 3000ms 变为 1500ms，并确认持续生产 |
| 普通权限兼容 BAT | 标准权限调用实际安装 BAT，返回 0，HWiNFO PID 与 INI 不变 |
| 进程中断 | BAT 和 PS1 都临时移走时，中断 HWiNFO，本体仍自动拉起新进程并持续生产；两文件按原哈希恢复 |
| 共享关闭 | 应用退出后以 SensorsSM=0 启动 HWiNFO，确认进程存在但共享不可读；原生命令恢复共享并证明时间继续推进 |
| 可读共享区持续停更 | 暂停上游进程，原进程被本体自动替换，新共享区恢复推进；无需测试脚本手动恢复旧进程 |
| 恢复原周期 | 本体将实际周期恢复到 3000ms |

最终恢复后的 23 条正常统一快照均为 HWiNFO Presented FPS；GPU／CPU 功耗的独立有效期正常。原 65 个受管传感器组状态没有差异。INI 的 37 个键值与测试前完全相同；文件字节不同仅涉及 PresentMon 行的位置和空行，因此没有声称整个文件哈希恢复一致。外部稳定模板及旧 PS1 哈希保持不变。

详细监控快照仍使用现场已开启的既有高频门，1Hz、每文件 2MiB、保留 2 文件；不转移到低频生命周期日志。生命周期只记录配置／恢复事件。

没有等待满 12 小时，不把人为共享关闭的恢复当作免费版真实到期验收；没有更改许可机制。未测试实际睡眠、真实跨用户凭据提权或自动浮动功耗写入，也未测 CPU 占比。
