# 监控读取交接与停止边界竞态修复（2026-10-16）

本轮以当前实际生产单例复现停止操作与 promise 交接交错时的旧数据回流，并按已有家族时间戳边界修复。生产修改仅 monitorData.ts；公开采集/读取 API 不变，没有新增源、硬件读取、轮询、线程、timer 或 IPC 命令类型，没有部署、重启或实机操作。

## 修改前负例

readViaSnapshot 已经解析和完成旧停止边界处理，控制副本也已生成，但 readMonitorSnapshot 的 promise continuation 尚未发布时，释放需求会发出 monitor.stop，推进实际停止时间。原 continuation 只核对 publicationVersion，不核对这个刚变化的停止边界，所以旧 top/FPS 仍被返回并进入显示。

用正常 JavaScript promise/microtask 交错和虚拟时钟复现三种情况：全部停止、只停 FPS、只停 top。停止命令均确实出现在惰性 IPC 记录中；修改前返回与显示均包含两个旧家族，修改后分别为：

| 操作 | 保留 top | 保留 FPS |
| --- | --- | --- |
| 全部停止 | 否 | 否 |
| 只停 FPS | 是 | 否 |
| 只停 top | 否 | 是 |

另用实际订阅回调复现：第一条或第二条显示通道回调发出停止时，后续通道/控制返回值仍可能沿用旧家族。本轮也检查这些窗口，并保留“更新 publicationVersion 赢得发布”的既有保护。

这里是冻结源码、合成快照和虚拟时间下的确定性负例，没有据此确认此前某台实机跳动的唯一原因。

## 修复

生产 owner 在发出停止命令时推进一个本地停止边界版本；真实发布者换会话并重置旧停止门时也推进。仅生产读取为自己的原始结果记录已经应用的边界版本，native 推送不增加逐包 WeakMap 记录，公开测试/控制 hub 不分配这份交接记录。

已有私有读取关联扩展为：本次原始 view、控制副本已经应用的版本，以及由 owner 提供的完成函数。公开字段上不挂这些信息。关联仍在结果返回前删除；正常读取只比较固定版本值，边界没有变化就直接使用原始 view。

边界改变时，完成函数给控制副本重新执行已有 applyStaleFloor。硬件、FPS、独立 Windows 核心/电池/风扇/文件系统/Global 上限仍按各自已有时间戳处理，不把缺失伪造成 0，也不把同一对象或同一 seq 当作新观察。尚未冻结的私有源可原地重判；已经被另一读者显示并冻结的源必须额外复制，避免修改历史只读对象。每位并发控制读者都携带自己的版本，不能因共享源已被前一读者刷新，就漏掉另一份控制副本。

生产分发还在两个显示通道回调之后比较固定版本；发生真实停止变化才重新处理，已有 pubVersion 保护优先保留新发布。部分家族失效后的通知继续遵守原 1Hz/200ms 预算，不为它开启新的采集或无条件刷新循环。测试等待相应预算后核对两通道最后结果；没有把“立即完成过滤”等同于每条部分失效通知都同步显示。

读完成通知中发出的停止也会在返回控制副本之前再核对一次。缺失私有关联的隔离复制回退保留，并使用同一个停止边界。

## 正常开销与异常成本

- 200 次普通读取：修改前后均为 200 次整快照复制，复制数组项均为 75,200；没有额外家族过滤。新增固定版本比较及小型私有关联有自身成本，不称为零成本。
- 200 次高频推送：0 次整快照复制、0 个读取关联、0 次读取完成过滤，键和有效性计算仍各 200 次，没有增加命令。
- 三个“复制完但尚未发布”的停止负例：仍只做原有的一次控制复制，重新应用边界后，失效家族不返回/不发布。
- 在已冻结共享源遇到停止的稀有场景，需要额外隔离复制。两个并发读者加回调停止的 fixture 共 4 次整快照复制，其中两次控制副本、两次异常显示处理；关联最终为 0。这是为了保留既有只读快照，未把这项成本隐藏。
- 旧四文件路径仍只读现有四个文件，没有第二路采集。

本轮不是 CPU 百分比或堆内存压测。计数描述具体函数工作，不能换算为整机降幅。
