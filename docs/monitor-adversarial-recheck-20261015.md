## 新确认并修正的四处问题

1. 同一游戏的 FPS 进入标记混入了采集 `generation`。原生会话、PID、出生标记都相同且真实观测持续更新时，仅改变采集代次，也会让 FPS 家族重新隐藏并等待 3 秒。修正 `src/bridge/monitorHudModel.ts`：现代包按原生会话/PID/出生标记标识游戏；没有出生标记的旧包仍保留代次隔离。真实进程、PID 复用、原生会话变化继续重新确认。
2. 新目标绑定后可以接收选择目标之前的 HWiNFO 观测，把上一目标的 FPS/LOW/曲线重新标成新 PID。修正 `native/monitor_frame_output.h` 并在唯一生产调用点传入既有 `nowMs`：新目标以选择时间及 Windows 进程出生时间作为观测下限。HWiNFO 整秒观测必须晚于下限；当前目标的实时 RTSS 观测可以立即进入原有流程。同一目标的连续读取不会重设下限。
3. 新的传输包裹内若带有较旧观测，原来能够倒退当前 FPS、LOW 或历史曲线。修正同一 `Output`：HWiNFO 与 RTSS 分别拒绝比已接受观测更早的时间戳；重复读取同一生产者时刻仍遵守原有有效期，不延长观测寿命。
4. 现代 FPS 包中的出生标记缺失、为零、格式错误或超出 uint64 范围时，原接收端可能把它丢弃后按较弱身份继续接受；字符串 PID 还会被数值转换接受。修正 `src/bridge/monitorData.ts`：现代观测包要求真实整数类型的有效 Windows PID，以及非零、规范、范围内的出生标记。没有现代观测/身份字段的旧协议仍保留原有有界兼容路径。这里校验的是统一发布者给出的身份格式，不是新增 OS 进程查询。

上述新问题先由独立反例在修复前产生失败记录，再修正生产源码。上一轮 TDP 等待态的 5 秒处理及共用工具进程排除规则均保留。
