# FPS 显示通知的状态收尾与定时器修复（2026-10-16）

本轮在现有 FPS 显示准入函数中复现并修复回调期间状态改变后的旧流程继续执行问题。生产修改仅限 monitorHudFpsVisibility.ts，继续消费已有真实快照，没有新增采集、轮询、线程或定时器类型，没有部署、重启或实机游戏操作。

## 修改前负例

FPS 完成进入等待、即将发布 ready=true 时，通知回调可能立即 dispose、reset、接纳 FPS=0，或接纳另一款游戏。原 refresh 在通知返回后仍按旧数据继续安排定时器。更换目标游戏触发 ready=false 的内部 reset 同样存在该窗口：回调处理了新状态后，旧 refresh 又覆盖 target 与首次观察时间。

冻结的修改前实际模块复现了 8 种情况：进入通知中的 dispose/reset/零 FPS/新游戏，以及目标变更通知中的相同四种动作。

- 关闭、重置或零 FPS 后仍遗留一个 timer，pending 仍为 true；修改后均为 0。
- 进入通知切到新游戏后，原流程会取消新游戏正确的截止定时器，再挂较早的旧截止时间；该样本累计安排 3 次，修改后 2 次。
- 目标变更通知再接纳第三款游戏时，原流程会覆盖第三款游戏的进入跟踪。后续真实数据已连续 3 秒却还不能展示；修改后保留最新目标，按原规则正常进入。

这些是实际函数、合成快照与虚拟时钟下的确定性复现，没有据此确认此前实机闪烁由该问题引起。

## 修复

每次外部 accept/reset/dispose 推进一个本地 revision。refresh 记住自己的 revision，在内部 reset 通知后、进入状态通知后分别核对。如果通知回调已经关闭、重置或接纳了更新状态，旧 refresh 立即结束，不覆盖新目标，也不再安排旧定时器。

现有 token 仍负责拒绝已取消的定时器回调。revision 与 token 分工不同：允许现有较早的安全定时器在新快照到达时继续服务，不因每次 accept 就取消重挂 timer。

保留原来的真实数据约定：FPS>=1 才能进入；进入需要墙钟等待和真实观察跨度均达到 3 秒；重复单份缓存不能满足进入；按原快照截止时间失效，不续期；预览 fixture 仍立即显示；所有 FPS 家族（包含锁帧上限）随主 FPS 隐藏。现有 5 秒基础丢失容忍没有调整。

## 验证与工作计数

6 个关闭/重置/零 FPS 场景：该样本累计安排次数由 2 次变为 1 次，动作后的剩余 timer 从 1 变为 0。两个新游戏场景累计安排次数由 3 次变为 2 次，保留新游戏自己的一份正确 timer。所有场景最终 dispose 后为 0；手工再次执行已取消回调也不会复活通知或 timer。正常流程 2000 次对照完全相同，没有减少或延长数据验证。

这些是异常路径的定时器工作次数与状态边界，不是 CPU 百分比测量，也不代表正常游戏场景的平均性能降幅。
