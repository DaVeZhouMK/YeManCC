# YeManCC 第二轮优化与评估报告（CCD / 降压 / 逻辑门，2026-07-31 R2）

承接第一轮验收（`docs/VERIFY-REPORT-2026-07-31.md`）。本轮目标：在已验证的基线上继续优化 CCD 控制链路、降压交互，并复验逻辑门修复。

---

## 1. CCD 核心控制 —— 评估发现 3 个问题，已修复并部署

### 1.1 g_ccdSeen 无界增长 + PID 复用漏应用（native/main.cpp）
- **问题**：`ccdApplyNew` 把见过的 PID 记入 `g_ccdSeen` 且永不清除。长期运行时集合无限增长；更严重的是 **PID 被系统复用**时，新进程拿到旧 PID 会被当作"已处理"而永远不被 CCD 限制（只有切一次模式才会全量重扫）。
- **修复**：`ccdWorker` 每 ~30 秒（25 × 1.2s）强制一次全量 `ccdApplyMode(mode)`，同时兜底清空重建 `g_ccdSeen`。PID 复用场景最迟 30 秒内被纠正。
- 附带收益：模式切换后新进程的亲和限制最长 1.2s 内生效（增量），30 秒兜底全量。

### 1.2 SetProcessAffinityMask 失败静默（native/main.cpp）
- **问题**：`ccdApplyToPid` 不检查返回值 —— 受保护/提权进程（杀软、系统组件等）设置失败时无任何痕迹。
- **修复**：返回错误码（0 成功 / -1 打开失败 / >0 设置错误码）；全量应用时统计打开失败与设置失败数，写入 app 日志（`[ccd] mode=N 应用完成: 打开失败=X 设置失败=Y`），不影响尽力而为的整体行为。

### 1.3 CCD worker 线程永不退出 / 无法重启（native/main.cpp）
- **问题**：`g_ccdStop` 从未被置位；若窗口销毁重建（托盘/常驻模式切换），worker 也不会重启。
- **修复**：WM_DESTROY 置 `g_ccdStop=true`；`ccdStartWorker()` 先重置 `g_ccdStop=false`，保证销毁重建后可正常重启。

### 1.4 前端状态持久化（CcdCard.vue）
- **问题**：手动应用 CCD 模式时只在"自动应用"开关打开时才写配置 → 开关关闭时重进页面档位丢失，UI 与实际脱节。
- **修复**：应用成功即持久化档位（enabled 标志保持原值），重进页面恢复上次档位。

**验收口径**：本轮 4 项均为代码审查 + 编译验证（BUILD_OK）；运行态行为依赖 app 重启后生效。真机拓扑与亲和性机制在第一轮已实测 PASS（全核 108.7% → 仅 CCD0 62.9% → 108.5%）。

## 2. CPU 降压 —— 评估结论 + 前端修正

### 2.1 AMD 读回：协议层面不可行（评估结论，非 bug）
- AMD MP1 邮箱 `set-coall`（0x36）是**只写命令**，SMU 无标准读回接口；`uv probe` 返回的 `current: 0` 为硬编码（YeManTdpCtl.py `amd_uv_probe`）。UXTU/ryzenadj 同样不读回，只信写入状态。
- 能验证的判据：SMU 邮箱接受状态（status==1 → "OK"）+ 退出码 —— 已实测 `uv set -8`/`0` 均 OK。
- Intel 路径（rdmsr 0x150 读回）才有真实当前值。**建议后续如需 AMD 当前值，前端以"最后应用档位"为准（已实现）。**

### 2.2 前端"未降压"误显示（UndervoltCard.vue）
- **问题**：AMD 下 probe 恒返 current=0 → 应用了降压档后卡片仍显示"未降压"；且关闭"自动应用"时档位不持久化，重进页面即丢失。
- **修复**：
  1. 应用成功即持久化档位（不依赖自动应用开关）；
  2. 挂载时优先用已记录的档位计算"当前"显示值（AMD 读回不可用，以配置为准）；
  3. 持久化失败不影响应用结果（独立 try/catch）。

- CCD 掩码为 ULONG_PTR（64 位），>64 逻辑线程或多处理器组机器上亲和掩码不覆盖第二组（本轮未改动，标注为已知边界）。
- AMD 降压无真读回（协议限制）；前端以持久化档位显示。
- CCD worker 全量刷新间隔 30s 为经验值，若进程频繁创建可调（`ccdWorker` 内 `fullCount >= 25`）。
