# Legion real Windows message queue clock boundary

Run from the mainline repository:

    node tools/legion_message_queue_platform_selftest.mjs

Optional `--out` must name a fresh direct child of the assigned MessageQueuePlatform evidence root. `--vcvars` selects the installed MSVC x64 setup batch. Every child process has a 45-second timeout; private-thread waits are bounded at 5 or 10 seconds. There is no full environment SET output, environment dump, or persisted inherited compiler environment.

The runner uses the actual production `native/legion_motion_message_clock.h`, directly included by MSVC. It extracts `legionMotionMessageReceiptTick` verbatim from current main.cpp, plus the exact production source-window constant. Only `inputCaptureLegionControllerMotionRoute()` is replaced by an explicit fixture boolean. GetMessageTime/GetTickCount64 are actual Win32 imports. Extraction locations, exact code, SHA256, production WM_INPUT entry call and epoch-store anchors are retained. Neither main.cpp nor its complete atomic/ownership/consumer path is executed. Unrelated concurrent main edits are allowed; the bound function and constant must remain identical.

A private worker creates its own queue and a message-only hidden window, signals readiness, and processes bounded requests from the sender. Both PostThreadMessage and PostMessage are exercised with real PeekMessage/GetMessage/GetMessageTime/GetTickCount64 calls. A sole consumer checks message presence before GetMessage to avoid an empty-queue wait. Window messages are also dispatched to the private WndProc. No visible window, RawInput registration, SendInput, device, settings, services, production application startup, DLL probing, actual sleep/wake or Neptune action is performed.

Cases include queue residence across 120-ms delay, PM_NOREMOVE timestamp retention, all posting/removal combinations, queue items before/after an actual GetTickCount64 epoch cutover, production 1500-ms freshness expiry, 24 fixed same-ms pairs, and route disable. Raw observations and every failed assertion are retained. Strict containment of the queue timestamp within sender GetTickCount64 brackets is an assumption under test; a mismatch is a reported platform finding. No tolerance/rebasing/retry is used to force green. Broad-age diagnostic normalization is distinct from the exact production bridge.

Signed GetMessageTime values preserve their actual 32-bit pattern. If the machine uptime does not expose negative actual values, that limitation is reported. Four synthetic signed bit patterns supplement arithmetic coverage and never count as actual OS negative/wrap observations. A true same-ms cutover witness is counted only if both real receipts equal the actual cutover. Missing witnesses are explicitly reported. Strict > rejects both messages at an uncertain equal tick. Each trial also waits for the next provably newer actual OS tick and verifies recovery. The previous >= implementation is compiled and run as a mutant in both configurations; a genuine same-tick OS counterexample and the declared rejection assertion are required to count a kill. Compile errors/crashes never count as kills.

WM_APP queue evidence is not WM_INPUT/HID or physical/firmware sample timing evidence. Hardware input, actual suspend/resume, HC end-to-end output and real controller sleep stability remain false/unverified. Compiler errors and infrastructure exceptions exit 2. Observed platform assumption failures preserve both configurations and exit 1; ordinary completion with stated boundaries exits 0.
